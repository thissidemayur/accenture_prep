# Accenture OS Preparation — High-Return Theory
## Placement-focused revision for an OS topic you studied earlier

> **Goal:** Rebuild the OS concepts that are most likely to help with Accenture-style technical MCQs and scenario questions.
>
> This is intentionally NOT a full Operating Systems textbook. The focus is **concept → keyword → question pattern**.

---

# 1. Process vs Thread — VERY HIGH PRIORITY

## Process

A **process** is a program in execution.

A process normally has its own:
- Address space
- Resources
- Process state
- PCB

Processes are more isolated from each other than threads in the same process.

## Thread

A **thread** is a unit of execution within a process.

Threads in the same process generally share:
- Code
- Data/global variables
- Heap
- Open resources such as file descriptors

Each thread has its own:
- Stack
- Program counter
- CPU registers

### Exam shortcut

```text
Process → separate address space
Thread  → shares process resources
```

If asked:

> "What do threads share?"

Think:

**Heap / code / global data**

If asked:

> "What is separate for each thread?"

Think:

**Stack / registers / program counter**

---

# 2. PCB

**PCB = Process Control Block**

The OS maintains process information in the PCB.

Common information includes:
- Process ID (PID)
- Process state
- Program counter
- CPU registers
- Scheduling information
- Memory-management information
- Open-file/resource information

### Exam pattern

> "Where does the OS store information needed to manage a process?"

→ **PCB**

---

# 3. Process States

The basic process lifecycle:

```text
New
 ↓
Ready
 ↓
Running
 ↓
Waiting / Blocked
 ↓
Ready
 ↓
Running
 ↓
Terminated
```

### Meaning

**New** → process is being created.

**Ready** → waiting for CPU.

**Running** → currently executing on CPU.

**Waiting/Blocked** → waiting for an event, usually I/O.

**Terminated** → execution has finished.

### Very common trap

```text
Ready    → waiting for CPU
Waiting  → waiting for event/I/O
```

Do not confuse them.

---

# 4. CPU Scheduling

CPU scheduling decides which ready process gets CPU time.

Important algorithms:

## FCFS

**FCFS = First-Come, First-Served**

- Non-preemptive
- Processes execute in arrival order
- Can suffer from convoy effect

## SJF

**SJF = Shortest Job First**

Chooses the process with the shortest CPU burst.

- Can minimize average waiting time under ideal assumptions
- Usually discussed as non-preemptive

## SRTF

**SRTF = Shortest Remaining Time First**

Preemptive version of shortest-job scheduling.

## Round Robin

Uses a **time quantum**.

Each process gets a small CPU time slice.

Think:

> **Time quantum → Round Robin**

## Priority Scheduling

CPU is assigned according to priority.

Can be:
- Preemptive
- Non-preemptive

### Placement shortcut

```text
Arrival order       → FCFS
Shortest job        → SJF
Shortest remaining  → SRTF
Time quantum        → Round Robin
Priority            → Priority Scheduling
```

---

# 5. Preemptive vs Non-Preemptive

## Preemptive

OS can take CPU away from a running process.

Useful when:
- Fast response is important
- High-priority work should run immediately

Examples:
- Round Robin
- SRTF
- Preemptive Priority

## Non-preemptive

Once a process gets CPU, it normally keeps it until:
- It finishes
- It blocks/waits

Examples:
- FCFS
- Traditional SJF

### Scenario pattern

> "High-priority process must get CPU immediately after becoming ready."

Think:

**Preemptive Priority Scheduling**

---

# 6. Context Switching

A **context switch** occurs when the CPU changes from one process/thread to another.

The OS must save the current execution context and restore the next one.

Important context includes:
- Program counter
- CPU registers
- Process state
- Scheduling-related information

Context switching has overhead because the CPU spends time switching rather than doing application work.

### Exam trap

Do not think:

> Context switch = process termination.

It is simply a switch between execution contexts.

---

# 7. System Calls

A user application cannot directly perform privileged kernel operations.

It uses a **system call** to request OS services.

Typical flow:

```text
User program
     ↓
System call
     ↓
Kernel mode
     ↓
OS performs privileged operation
     ↓
Return to user mode
```

Examples:
- `fork()`
- `exec()`
- `wait()`
- `open()`
- `read()`
- `write()`
- `close()`

### Exam shortcut

> User program requests OS service → **system call**

> System call enters privileged execution → **kernel mode**

---

# 8. User Mode vs Kernel Mode

## User Mode

Applications run with restricted privileges.

## Kernel Mode

The OS kernel can perform privileged operations.

Why?

> To prevent ordinary applications from directly damaging critical system resources.

### Memory trick

```text
Application → User mode
OS/kernel → Kernel mode
Privileged operation → Kernel mode
```

---

# 9. fork() and exec() — VERY HIGH PRIORITY

This is directly present in your screenshot.

## fork()

Creates a new process.

After `fork()`:

- Parent continues
- Child also continues
- They have different process IDs

## exec()

Loads/replaces the current process image with another program.

It does **not** create another process.

### Classic combination

```text
fork()
  ↓
create child
  ↓
exec()
  ↓
child runs another program
```

### Memorize

> **fork = create process**  
> **exec = replace program**

This distinction is extremely important.

---

# 10. wait()

`wait()` allows a parent process to wait for a child process to terminate and collect its termination status.

Typical pattern:

```text
Parent
  ↓
fork()
  ↓
Child runs
  ↓
Child exits
  ↓
Parent wait()
```

### Keyword

> Parent waits for child → **wait()**

---

# 11. Orphan vs Zombie

This is a high-return distinction.

## Orphan

A child continues running after its parent exits.

The child is adopted by a system process such as PID 1 on modern Linux systems.

Think:

> **Parent dies first → Orphan**

## Zombie

A child has already terminated, but its parent has not yet collected its exit status.

Think:

> **Child dies first + parent hasn't wait()ed → Zombie**

### Memory trick

```text
Parent dies → ORPHAN

Child dies + exit status not collected → ZOMBIE
```

---

# 12. Process Creation Functions

For the level relevant to your questions:

- `fork()` → create a child process
- `exec*()` → replace process image
- `wait()/waitpid()` → wait/reap child
- `exit()` → terminate process

Do not confuse:

```text
fork()  ≠ exec()
```

---

# 13. IPC

**IPC = Inter-Process Communication**

Processes normally have separate address spaces, so they need mechanisms to communicate.

Important IPC mechanisms:

### Pipe

Useful for communication between related processes.

### Message Queue

Processes exchange discrete messages.

Keyword:

> **Structured/asynchronous messages → Message Queue**

### Shared Memory

Processes communicate through a shared memory region.

Very fast, but synchronization is needed.

### Socket

Useful for communication between processes, including across machines.

### Signal

Used mainly for event/notification-style communication.

---

# 14. Synchronization

When multiple execution units access shared data, a race condition can occur.

## Critical Section

The portion of code where shared data/resource is accessed.

Goal:

> Only the allowed execution unit enters the critical section at a time.

---

# 15. Mutex

**Mutex = Mutual Exclusion**

A mutex allows only one owner at a time.

Think:

> **One-at-a-time access → Mutex**

For inter-process use, the mutex must be configured for process sharing; mutexes are especially common for thread synchronization.

---

# 16. Semaphore

A semaphore is a synchronization primitive represented by a counter.

Two common conceptual forms:

- Binary semaphore → 0/1 style
- Counting semaphore → multiple permits

Think:

> **Limited number of permits/resources → Counting semaphore**

Do not automatically answer "mutex" for every synchronization question.

---

# 17. Mutex vs Semaphore

```text
Mutex
→ mutual exclusion
→ ownership concept
→ usually one owner

Counting semaphore
→ controls number of available permits/resources
→ no simple ownership model like a mutex
```

### Question clues

> "Only one thread can access"

→ Mutex

> "At most N processes can use a resource"

→ Counting semaphore

---

# 18. Race Condition

A **race condition** occurs when the result depends on the timing/interleaving of concurrent operations.

Example:

```text
Thread A reads x
Thread B reads x
Thread A updates x
Thread B updates x
```

The final result may be incorrect.

Typical solutions:
- Mutex
- Semaphore
- Other synchronization mechanisms

---

# 19. Deadlock

A deadlock occurs when processes/threads are permanently waiting for resources held by one another.

The classic four necessary conditions are:

1. **Mutual exclusion**
2. **Hold and wait**
3. **No preemption**
4. **Circular wait**

Memory:

> **M H N C**

You do not need deep deadlock algorithms initially; know the four conditions and the basic definition.

---

# 20. Memory Management

Each process needs memory.

The OS manages:
- Allocation
- Protection
- Virtual memory
- Address translation

A process normally cannot freely access another process's protected memory.

---

# 21. Virtual Memory

Virtual memory gives processes the illusion of a large, private address space.

It allows the OS to use disk-backed storage as an extension of physical memory.

Important concepts:
- Pages
- Frames
- Page tables
- Page faults
- TLB

---

# 22. Paging

Virtual memory is commonly divided into fixed-size **pages**.

Physical memory is divided into fixed-size **frames**.

```text
Virtual memory → Pages
Physical memory → Frames
```

A page table maps virtual pages to physical frames.

---

# 23. Page Fault

A page fault occurs when a process accesses a page that is not currently available in the required physical memory location.

The OS handles the fault and may need to bring the page from secondary storage.

### Exam clue

> "Required page is not currently in physical memory"

→ **Page fault**

A page fault is not automatically a program error.

---

# 24. Segmentation Fault

A segmentation fault occurs when a process performs an invalid memory access, such as accessing memory it is not permitted to access.

Typical result:

> **SIGSEGV**

### Do not confuse

```text
Page fault
→ virtual-memory event
→ can be handled normally by OS

Segmentation fault
→ invalid/prohibited memory access
→ usually terminates the offending process
```

---

# 25. File Descriptors

A **file descriptor (FD)** is a small integer used by a process to refer to an open file or I/O resource.

Standard descriptors:

```text
0 → stdin
1 → stdout
2 → stderr
```

Important system calls:

- `open()` → open resource/file
- `read()` → read
- `write()` → write
- `close()` → close
- `dup2()` → duplicate/redirect a file descriptor

---

# 26. stdout Redirection

To redirect standard output to a file:

Conceptually:

```text
open(file)
   ↓
dup2(file_fd, STDOUT_FILENO)
   ↓
printf()/write() → file
```

### Exam clue

> "Redirect stdout to a file"

Think:

**open() + dup2()**

---

# 27. Permissions

Linux permissions are commonly represented for:

```text
User
Group
Others
```

And:

```text
r → read
w → write
x → execute
```

Example:

```text
rwxr-xr--
```

Means:

- Owner → rwx
- Group → r-x
- Others → r--
